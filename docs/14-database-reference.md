# Database Reference

Single shared Postgres (Supabase + pooler). Tracked migrations in `load/migrations/`, applied in order by `node load/migrate.js` (`npm run db:migrate`). All DDL is idempotent (`IF NOT EXISTS`).

### Migration 037 — verified evidence

Changes the ranking ledger from documentation to enforcement:

- **`ranking_events`**: `+ source`, `+ evidence jsonb`, `+ verified_at`; and a
  **`BEFORE INSERT` trigger `ranking_events_require_verification`** that raises
  when `verified_by` is NULL or blank — **for every role, including the owner**.
  No score can be written without a named actor vouching for it.
- **`ranking_scores`**: primary key corrected from `user_id` to
  `(tenant_id, user_id)`. It was `user_id` alone, and `recompute_ranking_scores`
  did `ON CONFLICT (user_id)` without refreshing `tenant_id`, so one row could be
  overwritten across two chapters.
- **`projects`**: `+ repo_full_name`, `+ evidence_state`
  (`provisional|verified|rejected`, default `provisional`), `+ verified_at`,
  `+ verified_by`, and `CHECK (status IN ('active','completed','archived'))`.
- **`student_roadmap_progress`**: `+ evidence_state`, `+ evidence_note`,
  `+ evidence_url`, `+ verified_by`, `+ verified_at`, and
  `CHECK (status IN ('active','completed'))`. The long-declared, never-written
  `evidence_source` column is now populated.
- **`github_events`**: `+ repository_name`, `+ student_id`, `+ tenant_id` with a
  partial index, backfilled from the existing jsonb payload.
- **`ranking_decayed_weight`** re-declared `STABLE` (it was `IMMUTABLE` while
  calling `now()`), with a real multi-step age curve.
- **`ranking_kind_cap(kind)`** added; `recompute_ranking_scores` now filters on
  `verified_by IS NOT NULL`, applies caps, fixes the conflict target, and
  **deletes** scores for users with no verified evidence left — so declining a
  claim genuinely lowers a standing instead of freezing it.
- `feature_flags.ranking_verified` seeded **false**.

Full rationale, weight table and known limits: **[`docs/20-verified-ranking.md`](20-verified-ranking.md)**.

**Any code reading `projects` or `student_roadmap_progress` as evidence MUST
filter on `evidence_state = 'verified'`.** Counted raw, a self-declared row is
indistinguishable from a confirmed one — that is the bug 037 exists to close.

**Read migrations 030/031/033 together with `docs/rls-rollout-runbook.md` before
changing anything about roles or policies.** Three facts that are easy to get
wrong:

1. The **owner** connection (`DATABASE_URL`, role `postgres`) has
   `rolbypassrls = true`, which overrides `FORCE ROW LEVEL SECURITY` entirely.
   Queries running on it are **never** filtered by any policy.
2. `tenant_isolation_policy` denies when `app.tenant_id` is unset. A scoped
   statement must therefore run through `scopedSql()` (`lib/db.js`), which wraps
   it in a transaction with `set_config(..., true)`.
3. `feature_flags` has no RLS on purpose, so `tenant_rls_enforced` is readable
   before a tenant is known — and so any chapter admin can read every chapter's
   flags. It holds configuration, not member data.

Tracked migrations are the single source of truth for schema — there is no ORM mirror. All server queries are parameterized `postgres` template strings via `getSql()` in `lib/db.js` (`{max:10,idle_timeout:10,prepare:false}` for the PgBouncer pooler); tenant config is memoized 60s in `queryTenant()`.

## Key relationships

- `profiles.tenant_id → tenants.id` is the tenancy root; every tenant query filters on it.
- `student_roadmap_progress.node_id → roadmap_nodes.id` (text keys, stable across tenants).
- `student_oss_contributions.project_id → open_source_projects.id`; webhook matches `owner/repo` + author login → profile/github_connection. `canonical_url` is the lower-cased, trailing-slash/files/comment-stripped PR or issue URL, unique per student so one contribution cannot be claimed twice.
- `repositories.student_id → profiles.user_id`; `repositories` is the tenant-scoped cache behind `GET /api/github/repos`, written by an authenticated GitHub listing (bulk upsert via `jsonb_to_recordset`). `github_repo_grants.(user_id, repo_full_name)` is what proves a project repository is owned/pushable — grants are **explicit only**, written by `POST /api/github/repos/verify` or `POST /api/github/repos`, not silently on every picker load. `projects.repo_full_name` is the one-claim-per-repo key.
- `mentor_sessions.mentor_id` stores `mentors.user_id` (not the uuid PK) — joins go through `profiles.user_id`.
- `verifiable_credentials.achievement_id → student_achievements.id`; existing share links retain the HMAC contract.
- `certificates(event_id, student_id)` is issued once per pair at check-in. Version 2 signs a canonical stored payload with the active tenant Ed25519 private key and verifies it with the retained public key; version 1 HMAC rows remain readable during migration. Certificate expiry/revocation and key revocation all fail public verification.
- `scoped_role_grants(tenant_id, user_id)` and grantor/revoker pairs reference profiles in the same tenant; a trigger validates that department/event/project scope IDs belong to that tenant.
- Workflow owner, handoff departments/actors, approval requester/decider, expense approval, and event-history actor/resource relationships use tenant-bound composite foreign keys where supported.

A partial unique index on `(tenant_id, user_id, target_role, COALESCE(department_id, zero-uuid)) WHERE status = 'open'` is the real single-open guard — two tabs cannot both land. Eligibility itself is not stored: it is computed live from `evidence_state = 'verified'` rows by `lib/role-requests.js`, and the 14-day cooldown is derived from the most recent decided row.

**Seat requests, enforced twice (098–099)**: the API refuses a request below the bar in `lib/role-requests.js`, and the database refuses it again. `role_request_verified_proof(user_id, tenant_id)` is the single SQL definition of "verified proof" (completed+verified roadmap nodes, verified projects, verified OSS merges, accepted forum answers). `role_requests_require_proof` raises `check_violation` (`ROLE_REQUEST_BELOW_BAR`) on an open row below the seat minimum (Core 3, Head 5); `department_memberships_require_core_proof` raises `CORE_REQUEST_BELOW_BAR` when `core_requested` turns true without 3 verified pieces. The thresholds are duplicated from `REQUIREMENTS` on purpose — a shared source would mean the database asking the application what the rule is, which is the bypass this closes. Both routes translate `23514` back into `NOT_ENOUGH_PROOF` (403), so a divergence between the two counts fails closed with the same answer.

**Append-only governance and retention (097)**: updates/deletes on `audit_logs`, `event_status_history`, and `approval_decisions` raise in the database. The runtime `loom_app` role has no direct `DELETE` on `audit_logs`; scheduled retention calls only `loom_private.prune_audit_logs_before(cutoff)`, which is `SECURITY DEFINER`, rejects cutoffs newer than 365 days, and enables the trigger exception only inside that function.

**Governance terms (048)**: `platform_admins.is_founder` + `.locked` + `.label` - permanent founder seats, immune to role-change APIs and, since 087, to `DELETE`/`TRUNCATE`/unlock at the database layer. `profiles.role_term_start/role_term_end` — global role term; `department_memberships.term_start/term_end` — department position term (an ended `dept_lead` row keeps history but stops conferring authority). `leadership_terms(id, tenant_id, user_id, role, vertical, department_id, starts_on, ends_on, status active|ended|expired, appointed_by, ended_reason, notified_at)` — append-only appointment history, with partial unique indexes preventing two active non-department terms per user/role and two active terms for the same department. `sponsorships.vertical` — scopes the finance snapshot. Existing rows are grandfathered (`role_term_end = NULL`); the rotation job is `node load/expire-terms.js [--apply]`.

**Feature-request issue links (049)**: `feature_requests.github_issue_number`, `.github_issue_url`, `.github_issue_repo`, `.github_issue_state`, `.github_issue_synced_at`, `.github_issue_error` — all nullable, so the GitHub bridge is inert until `GITHUB_ISSUES_REPO`/`GITHUB_ISSUES_TOKEN` are configured. A partial unique index on `(github_issue_repo, github_issue_number)` prevents two ideas claiming one issue. `github_issue_error` stores the last human-readable failure (never the token or the provider body) so an admin can retry from the board. The bridge is best-effort by design: the request is saved and audited before any network call, and the webhook ingestion path is deliberately untouched.

**Email verification (050)**: `profiles.email_verified_at` + `.email_verification_source` record an OPTIONAL trust signal — no account is gated on it, and there is no college-domain allowlist. `email_verification_tokens(user_id, tenant_id, email, token_hash unique, expires_at, used_at)` stores only SHA-256 hashes, so a database read cannot be replayed as a working link. Tokens are single-use, expire in 24h, and older unused rows are marked used when a new link is requested. Sending uses a transactional provider (Resend) selected by env; Supabase's shared SMTP is intentionally not used because its rate limit is not viable in production.

**OSS personalization + repo grants (051)**: `profiles.oss_level` (`beginner|intermediate|advanced`, nullable); `open_source_projects` gains `topics[]`, `contributing_url`, `homepage`, `pushed_at`, `metadata_synced_at`, and `is_active` so the student portal can rank and filter by real, honestly-dated GitHub metadata; `repositories` becomes the tenant-scoped cache behind `GET /api/github/repos` (unique `(student_id, lower(full_name))`); `student_oss_contributions` gains `canonical_url` and a partial unique index so `/pull/12`, `/pull/12/`, `/pull/12/files` and comment variants are one contribution per student. `certificates` gains `signature` and `revoked_at`; the signature is an HMAC over immutable fields, so a database edit cannot masquerade as an authentic certificate.

**Catalogue identity (052)**: GitHub owner/repo names are case-insensitive, so `open_source_projects` now has a unique index on `lower(owner || '/' || repo_name)`. The migration keeps the oldest row and deletes a duplicate only when no `student_oss_contributions` row points at it; a referenced duplicate is left for a human rather than silently moving evidence. The curation API still upserts on `github_repo_url`, and a case-variant seed cannot add a second picker row.

**Collective master planner (053, 054, 055)**: `planner_weeks((COALESCE(tenant_id, all-zero)) , academic_year, week_number unique, starts_on, ends_on, theme, delivery_mode live|deferred|async|project|assessment, is_protected, is_relaxation, notes)` — one row per week of the 28-week 2026-27 calendar (`is_relaxation` marks 6/7; `is_protected` marks the 7/8 exam block); `planner_sessions((tenant_id, academic_year, track_domain, curriculum_ref) unique where ref not null, week_number, title, description, session_kind, day_of_week 1-7 nullable, starts_time/ends_time, delivery_mode, is_required, is_relaxation, sort_order, notes, owner_user_id nullable -> profiles)` — the curriculum sessions across the six wings (`track_domain`: `dsa`, `ai_ml`, `cybersecurity`, `web`, `embedded`, `blockchain`; `general` for society coordination). `owner_user_id` (055, converted to text by 058 to match `profiles.user_id`) is the accountable member for a session: every lead-and-above tier runs the planner, and `PATCH /api/planner {action:"reassign"}` moves a departing holder's rows (or the null/unassigned bucket) to a successor in one step instead of re-typing the plan. A session is "deferred" when `day_of_week` is NULL or its derived date lands in the relaxation window. `events` gains `planner_year`, `planner_week`, `planner_kind`, `planner_ref` (unique per tenant where set) and `planner_status` — the link that places a society milestone on the calendar without duplicating the registration flow. Seeded idempotently from `load/data/loom-collective-planner-2026.json` by `node load/seed-planner.js`. 054 recreates both policies with the fail-closed 031/042 expression (`tenant_id::text = current_setting('app.tenant_id', true)`).

**Guided seat handover (056)**: `lead_handovers(id, tenant_id, from_user_id -> profiles, to_user_id -> profiles, role dept_lead|vertical_lead|admin, department_id nullable -> departments, vertical, brief jsonb {summary, responsibilities, activeWork, risks, contacts}, transfer_planner, transfer_event_ops, transfer_head_slot, transfer_tasks, status draft|submitted|completed|cancelled|rejected, review_note, created_by, submitted_at, reviewed_at/by, completed_at/by)` - one row per transition. A partial unique index allows only one draft-or-submitted handover per outgoing lead. Scope is derived server-side from the outgoing profile (department membership for a head, vertical for a VL); the successor must already sit inside that scope. Admin approval runs `lib/handover.js applyHandoverTransfer` in one transaction: promotes the successor, demotes the outgoing account, closes and opens `leadership_terms`, moves the department slot, `planner_sessions.owner_user_id`, active `event_ops_tasks.owner_id`, and (101, `transfer_tasks`) only the outgoing head's own `assigned/in_progress/blocked` `department_tasks` in the department being handed over, then writes audit + notifications. Member assignments are never rewritten: a handover changes who leads, not who does what. Fail-closed tenant RLS.
